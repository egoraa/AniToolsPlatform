# Конфиг модуля: второй канал настройки, приходящий до initialize

Дата: 2026-08-09. Статус: спека согласована, план реализации написан
(`2026-08-09-module-config-plan.md`), оба документа прошли ревю 2026-08-10.

## Задача

Модулю иногда нужно передать настройку, которую свойство выразить не может. Требования, собранные
у автора задачи, — все четыре одновременно:

1. **Не скаляр.** Список, таблица, вложенный объект: карта каналов, матрица, набор правил.
2. **Нужен раньше `initialize`.** Значение описывает устройство модуля, а не его поведение.
3. **Не редактируется на ходу** и не должен занимать строку в сетке свойств инспектора.
4. **Общий на несколько модулей** — дублировать один и тот же блок в каждом узле не хочется.

Почему существующие каналы не подходят:

- **Свойство** — скаляр с кодеком в строку и обратно (`property_base::to_string`/`from_string`,
  `property_kind` = JSON-тип значения). Ничего, кроме скаляра, туда не попадает: `blob`-свойство
  прямо запрещено в обоих мостах. Свойство редактируется живым и показывается в инспекторе — то
  есть нарушает и (1), и (3).
- **Аргументы конструктора, привязанные при регистрации** (`module_factory<TModule, TArgs...>`)
  задаются один раз на фабрику: «другой конфиг» означает «другая регистрация», а не другой
  экземпляр. Нарушает саму идею пер-экземплярной настройки.
- **`service_directory`** доступен только из `initialize`, то есть уже после `connect`. Нарушает (2).

Обратная совместимость не требуется: проект закрыт, пользовательских модулей нет.

## Решение

Третья объявляемая сущность рядом с портами и свойствами: **структурированное значение, приходящее
в конструктор модуля**. Конструктор — единственная точка, которая раньше и `connect`, и `initialize`,
и именно там вызываются `make<>()`, объявляющие порты.

Порты, зависящие от конфига, в объём **не входят**, но выбранная точка доставки оставляет для них
дверь открытой в самом сильном смысле: C++-модуль сможет объявлять порты от конфига без единой новой
правки платформы. Статикой останется только C-путь, где дескриптор пер-регистрационный, — это
отдельная будущая задача.

## 1. Тип значения: `atp::config_value`

Новый заголовок `include/atp/config_value.hpp`, рядом с `module_context.hpp`. Часть SDK
(`atp_platform`), но **не** часть зонтика `include/atp/io.hpp`: это не сущность io-слоя, портом не
является.

Закрытый вариант из семи форм: `null`, `bool`, `std::int64_t`, `double`, `std::string`, массив,
объект.

**Целое и вещественное разделены намеренно.** Тот же довод, по которому модель конфига хранит
значения узлами JSON, а не строками, и `5` не сливается с `"5"`: конфиг, где написано `3`, — это
счётчик, а не `3.0`. Кроме того, набор типов портов уже различает `i64` и `f64`.

**Объект хранится как `std::vector<std::pair<std::string, config_value>>`, а не как `map`.** Довод —
воспроизводимость обхода, тот же, что и у `__newindex`-прокси в Lua-пакете: один и тот же вход обязан
давать одни и те же хэндлы плоского индекса C-пути и один и тот же порядок вставки в словарь моста.

Чего это **не** даёт, чтобы не обещать лишнего: порядка ключей **из файла**. Документ читается как
`nlohmann::json`, то есть на `std::map`, и ключи отсортированы уже к моменту разбора — доксблок
`encode` (`config_model.hpp`) сам это признаёт про алиасы `expose`. Так что `config_value` сохраняет
порядок, в котором ему дали значение, а не написанный автором; сохранить второй означало бы читать
весь документ как `ordered_json`, а это подпись `validate`, `decode`, `encode`, MCP и проект разом —
см. «Вне объёма».

Построение — две статические фабрики и неявные скаляры, чтобы запись повторяла форму самого конфига:

```cpp
using cv = atp::config_value;

const cv root = cv::object({
    {"channels", cv::array({1, 2})},
    {"rate", 48000.0},
    {"name", "rig"},
    {"muted", true},
});
```

```cpp
static config_value array(std::initializer_list<config_value> items);
static config_value object(std::initializer_list<std::pair<std::string, config_value>> entries);
```

Конструкторы скаляров **не** `explicit` — иначе каждый элемент пришлось бы называть по имени типа и запись
теряет весь смысл. Целочисленный — шаблон по `std::integral` (кроме `bool`), потому что литерал `1` имеет
тип `int` и до `std::int64_t` сам не доедет. Символьные типы шаблон захватывает вместе со всеми
остальными, так что `config_value('x')` — целое `120`; форм с семантикой символа у конфига нет, и это
записано, а не оставлено на удивление.

**Перегрузка `config_value(const char*)` обязательна.** Без неё строковый литерал уходит в
`config_value(bool)`: указатель конвертируется в `bool` лучше, чем в `std::string`, и `{"name", "rig"}`
молча становится `true`. Ошибка бесшумная, поэтому на неё нужен отдельный тест, а не только перегрузка.

Доступ по конвенции репозитория (`try_` — не бросающий вариант):

```cpp
[[nodiscard]] bool is_null() const noexcept;      // is_bool, is_int, is_double, is_string,
                                                  // is_array, is_object
[[nodiscard]] std::size_t size() const noexcept;  // массив и объект, иначе 0
[[nodiscard]] const config_value* find(std::string_view key) const noexcept;   // nullptr
[[nodiscard]] const config_value& at(std::string_view key) const;             // бросает
[[nodiscard]] const config_value& operator[](std::size_t i) const;            // массив и объект
[[nodiscard]] std::string_view key_at(std::size_t i) const noexcept;          // ключ i-й пары
[[nodiscard]] std::int64_t as_int() const;              // бросает, называя найденную форму
[[nodiscard]] std::optional<std::int64_t> try_as_int() const noexcept;
[[nodiscard]] std::int64_t int_at(std::string_view key) const;   // бросает, называя ключ
template <typename T> [[nodiscard]] T value(std::string_view key, T fallback) const;
```

**Ни парсера, ни `dump()` в SDK нет.** Это ограничение, ради которого тип и заводится: подпись
`create()` не может назвать `nlohmann::json`, иначе `atp_platform` утянет nlohmann в каждый плагин —
ровно то, ради чего `atp_runtime` не экспортируется (`cmake/Install.cmake`). Преобразование
`nlohmann::json` → `config_value` живёт в `atp_runtime`, новый заголовок
`src/runtime/include/atp/runtime/config_value_json.hpp`. Единственное место, где преобразование может
не сойтись: `uint64_t` выше `int64_t` max, который в закрытом наборе форм не выражается. Такое число —
`bad_config`, называющий ключ, а не молчаливое переполнение.

Ошибки чтения — новый `atp::bad_config : std::runtime_error`. Модуль читает конфиг в конструкторе, и
сообщение об ошибке — всё, что автор увидит, поэтому оно обязано называть ключ. Полный путь внутри
дерева (`"channels[2].rate"`) для этого **не** заводится: он потребовал бы, чтобы значение знало
своего родителя, а это ссылки внутри типа-значения и цена не по задаче. Вместо этого ключ называет
тот вызов, который его и так знает — `int_at("rate")` бросает «'rate' is not an integer (found
string)», тогда как `as_int()` на уже добытом значении сообщает только найденную форму. Отсюда пара
уровней доступа: `at`/`as_*` для значения в руках и `*_at(key)` для чтения по ключу.

## 2. Формат файла

### Узел модуля

```json
{ "module": "resampler", "config": { "channels": [1, 2, 6] } }
{ "module": "resampler", "config": "rig" }
```

- **Объект** — конфиг на месте.
- **Строка** — всегда ссылка, никогда не литерал. От этого зависит однозначность грамматики ниже;
  конфиг, который сам по себе строка, записывается как `{"value": "…"}`.
- Ключа нет — модуль получает `config_value` формы `null`. Отсутствующий и пустой объект различимы
  намеренно: модуль вправе на это опереться.

Массив в качестве значения `"config"` не допускается — только объект: иначе «строка = ссылка»
перестаёт быть простым правилом. Массивы живут внутри объекта или внутри разделяемого блока.

### Верхнеуровневый блок

```json
"configs": { "rig": { "channels": [1, 2, 6] } }
```

**Запись сама обязана быть объектом**, её содержимое — произвольный JSON без схемы, в этом и смысл.
Ограничение на корень выглядит лишним (двусмысленности с ключом `"config"` тут нет), но без него
гарантия, на которую опирается конструктор модуля, зависела бы от написания: инлайн-конфиг обязан быть
объектом, а тот же конфиг через ссылку приезжал бы массивом или скаляром, и модуль должен был бы
проверять форму корня — то есть писать код ровно про то, какой синтаксис выбрал автор файла. Одно
правило дешевле: **корень конфига — всегда объект или `null`**, и это то, на что модуль вправе
опереться. Массив, который хочется разделить, оборачивается ключом.

### Грамматика строки

Строка разбирается по **первому** двоеточию:

```
"rig"                → configs.rig   — умолчание, префикса нет
"file:rig.json"      → ошибка: источник пока один
"<что угодно>:…"     → ошибка валидатора, называющая префикс
```

Разбор по первому разделителю — не изобретение: `parse_property_override`
(`runtime/property_override.hpp`) уже делит «path.prop=value» по первому `=`, а затем по последнему
`.`.

**Сейчас реализуется только грамматика и единственный источник — умолчание.** Любой префикс —
ошибка валидатора с внятным текстом. Новый источник впоследствии стоит один `case` и ноль правок
схемы; `file:` и `literal:` обсуждались и сознательно отложены (см. «Вне объёма»).

Имя записи в `configs` обязано быть без двоеточия — проверка валидатора в одну строку, снимающая
всякую двусмысленность.

### Схема

`runtime::config_schema_version` 3.1 → **3.2**. Ключ добавляется, форма существующих не меняется,
поэтому минорный шаг: конфиг 3.2 не читается хостом 3.1, конфиг 3.1 читается хостом 3.2 без изменений.

### Валидатор

В `config_validator.hpp`:

- `"config"` вносится в список разрешённых ключей узла модуля, `"configs"` — документа (отказ по
  незнакомому ключу — `config_validator.hpp:33`).
- `"config"` обязан быть объектом или строкой; иначе ошибка, называющая фактический тип.
- Строка: разбор грамматики; неизвестный префикс — ошибка, называющая префикс; имя без префикса —
  проверка существования записи в `"configs"` с ошибкой, называющей имя.
- Ключи `"configs"` — на отсутствие двоеточия, значения — на то, что каждое является объектом.
- Содержимое записей `"configs"` **не проверяется** ничем: у него нет схемы по определению.

Одна деталь про порядок проверок: сам блок `"configs"` разбирается раньше пайплайна, и если он не
объект, набор известных имён пуст — тогда каждая ссылка добавила бы вторую ошибку про висячее имя
поверх первой про сломанный блок. Проверка ссылок поэтому пропускается, когда блок разобрать не
удалось: сообщение должно называть причину один раз.

### Модель

`module_node` получает **одно** поле:

```cpp
std::optional<nlohmann::json> config;
```

Хранится **дословно как записано** — строка остаётся строкой, объект объектом. Тогда
`encode` — это `j["config"] = *config;`, и инвариант `encode(decode(doc)) == doc` выполняется без
всякой отдельной логики; разворачивать ссылку в объект при сохранении нельзя, и хранение исходного
написания — самый дешёвый способ этого не сделать.

`config` (документ) получает `std::vector<std::pair<std::string, nlohmann::json>> configs;`, тоже
дословно.

Разрешение ссылки и преобразование в `config_value` происходят **в билдере**, не в модели. Модель
остаётся JSON-образной ровно как сейчас для свойств
(`std::vector<std::pair<std::string, nlohmann::json>> properties`), а `config_value` появляется
только на границе с `create()`.

## 3. Доставка: подпись `create`

```cpp
[[nodiscard]] virtual module_ptr create(const config_value& cfg) const = 0;
```

Виртуальная функция плагинного ABI ⇒ `plugin_abi` **10 → 11**. Вместе с ней правится
`atp_require_plugin_abi(10)` в `templates/plugin/`, иначе джоба `out-of-tree plugin` перестанет
конфигурироваться — что и есть задуманная обратная связь, а не поломка.

**Параметр у `create` однажды уже был и был убран** — это надо сказать вслух, потому что иначе история
ABI в `plugin.hpp` читается как ошибка: пункт 6 там гласит «create(config) carrying per-instance
parameters as a config string», а пункт 8 заменил его свойствами. Возвращается **не** то же самое.
Тогда через `create` ехали пер-экземплярные **скаляры**, и свойства сделали это лучше по всем четырём
пунктам задачи: их видно в инспекторе, они правятся живыми, у них есть кодек в строку и обратно. Ни
одно из этих улучшений не касается значения, которое не скаляр, нужно раньше `initialize` и живым не
правится, — а именно то, что убрало пункт 6, и оставило нишу, которую закрывает 11.

Модуль подключается к каналу, только если хочет:

```cpp
if constexpr (std::constructible_from<TModule, const TArgs&..., const config_value&>) {
    new TModule(args..., cfg);
} else {
    new TModule(args...);
}
```

Ни один существующий модуль не меняется. Конфиг встаёт **после** аргументов, привязанных при
регистрации, — те остаются как были.

Значение по умолчанию на виртуальной функции **не ставится**: у виртуальных оно берётся от
статического типа и это классическая ловушка. Вместо этого удобную перегрузку с пустым конфигом
сохраняет `module_registry::create(name)`, чтобы тесты и `add_module` студии не таскали пустышку
руками.

Затрагиваемые вызывающие:

| Место | Правка |
|---|---|
| `include/atp/module_factory_base.hpp:35` | подпись + доксблок (он сейчас прямо обещает «Takes no parameters») |
| `include/atp/module_factory.hpp:56` | `if constexpr` выше |
| `include/atp/module_registry.hpp:83,89` | параметр + перегрузка с умолчанием |
| `include/atp/module_registry.hpp:203` | оборачивающая фабрика с пином библиотеки — проброс |
| `src/runtime/include/atp/c_module.hpp:762` | `c_module_factory::create` — проброс в `c_module` |
| `src/studio/include/atp/studio/module_manager.hpp:223` | пробный экземпляр для чтения портов — пустой конфиг |
| `tests/platform/module_factory_tests.cpp:85,88,95,100,107,108,118` | семь прямых вызовов `factory.create()` |
| `include/atp/plugin.hpp` | `plugin_abi` 10 → 11 + строка истории |
| `templates/plugin/CMakeLists.txt` | `atp_require_plugin_abi(11)` |
| `templates/plugin/README.md:17` | тот же номер в тексте |
| `cmake/AniToolsPlatformConfig.cmake.in:21` | тот же номер в примере доккомментария |

Прямые вызовы `factory.create()` из тестов **правятся**, а не прикрываются перегрузкой без параметра
на самой фабрике: удобная перегрузка есть у `module_registry`, где она обслуживает вызывающих, которым
конфиг взять негде, а на `module_factory` та же перегрузка означала бы, что вызывающий может бесшумно
потерять конфиг, который у него был.

В билдере (`pipeline_builder.hpp:65`) порядок становится `create(cfg)` → `apply_properties` → `add`.
Ошибку чтения конфига бросает конструктор модуля, а `build_group` уже оборачивает её контекстом
«module 'x' in group 'y'» — нового обращения с ошибками не нужно.

## 4. C-путь и мосты

### Аксессоры

`atp_api` получает семь дописанных **в конец** колбэков, за `struct_size`, — **без бампа
`ATP_C_ABI`**: `plugin_c.h:140` прямо объявляет добавление колбэков штатным способом роста.

```c
uint32_t (*config_root)(atp_ctx* ctx);
int      (*config_kind)(atp_ctx* ctx, uint32_t node);          /* atp_config_kind */
uint32_t (*config_size)(atp_ctx* ctx, uint32_t node);          /* массив/объект, иначе 0 */
int      (*config_key_at)(atp_ctx* ctx, uint32_t node, uint32_t i,
                          const char** out, size_t* len);
uint32_t (*config_child_at)(atp_ctx* ctx, uint32_t node, uint32_t i);
uint32_t (*config_find)(atp_ctx* ctx, uint32_t node, const char* key, size_t len);
int      (*config_value_of)(atp_ctx* ctx, uint32_t node, atp_value* out);
```

Узел адресуется непрозрачным `uint32_t`. Ноль зарезервирован под «узла нет» (`ATP_CONFIG_NONE`) —
его возвращают `config_find` и `config_child_at` при промахе, и корень нулём быть не может, так что
проверка результата у автора одна и та же во всех случаях. Скаляры выдаются существующим `atp_value`,
и **ни одной аллокации через границу** не происходит.

**Текст конфига живёт всё время жизни модуля, а не до следующего чтения.** Это сильнее контракта
портов, и намеренно: текст порта транзиентен потому, что он — копия, снятая в момент чтения в общий
scratch-буфер, тогда как строка конфига уже лежит в дереве `config_value`, которое модуль держит от
конструктора до деструктора. Отдать указатель прямо внутрь дерева и дешевле, и безопаснее; выдача
через scratch дала бы более слабую гарантию бесплатно и вдобавок странную асимметрию внутри одного
набора колбэков — `config_key_at` возвращает указатель в `std::string` дерева, то есть ключи были бы
вечными, а значения умирали бы от постороннего `get_input` на том же `ctx`.

Новое перечисление `atp_config_kind` повторяет семь форм `config_value`. Из этих семи `config_value_of`
осмысленно только для четырёх скалярных: в `atp_kind` нет ни null, ни контейнера, поэтому на `null`,
массиве и объекте вызов **отказывает и `*out` не трогает**. Без этой фразы каждый автор чужого
языка угадывает по-своему.

**Ловушка реализации, а не спеки, но цена ошибки бесшумная.** Хостовый `guarded` (`c_module.hpp:601`)
— булев: он делает `return body(self) ? 1 : 0`, потому что все восемь существующих колбэков отвечают
успехом или отказом. Четыре из семи новых возвращают хэндл, а `config_kind` — номер формы, и через
булев `guarded` `ATP_CONFIG_OBJECT` превратился бы в `1`, то есть в `ATP_CONFIG_BOOL`, а любой хэндл —
в единицу, то есть в корень. Нужен **второй** guard, возвращающий значение с передаваемым значением
отказа; булев остаётся как есть, на его `? 1 : 0` держится существующая таблица.

**Отвергнутая альтернатива:** отдать конфиг одной строкой JSON. У Lua нет встроенного парсера —
пришлось бы вендорить его в пакет, что дороже семи указателей.

Конфиг обязан быть читаемым уже внутри `desc.create` (`c_module.hpp:372`) — это C-аналог
конструктора. Значит `c_module` кладёт `config_value` в себя **до** вызова.

### Мосты

Каждый мост обходит дерево **один раз при создании экземпляра** и материализует родное значение:
`dict`/`list` в Python, таблицу в Lua. Автор скрипта видит обычный словарь, а не хэндлы и пути.

Одна честная потеря: таблица Lua порядок ключей не хранит, тогда как `config_value` и `dict` Python
хранят порядок, в котором значение пришло. Это записать в `docs/architecture.md`, а не оставить на
догадку — и вместе с оговоркой из раздела 1, что этот порядок и так не тот, что в файле.

### Зеркала

`templates/plugin_rust/src/abi.rs` (рукописное зеркало заголовка) и
`tests/platform/plugin_c_layout_tests.cpp` (закрепление размеров и смещений) правятся **парой** —
это уже установленное правило репозитория.

## 5. Студия

- `project` возит блок каждого модуля и документный `configs` через сохранение **сам, без единой
  правки**: он держит `runtime::config` и делает save, open и обе стороны undo/redo через
  `runtime::encode`/`decode` (`project.hpp:49,67,106,728,744`). Дословное хранение из раздела 2 делает
  круговой обход бесплатным, и undo вместе с ним.
- Словарь MCP не трогается, и трогать там **тоже нечего**: `document_tools.hpp:94` отдаёт
  `runtime::encode(ws.project().config())` целиком, так что конфиг появляется в `get_document` сам.
- Редактирование — **отдельная панель JSON** в инспекторе, не строка в сетке свойств. Требование (3)
  выполняется само: конфиг не является свойством, и инспектор его в сетке не видит.
- **При работающем пайплайне конфиг доступен только на чтение** — в отличие от свойств, которые
  остаются живыми. Это не новое правило, а следствие существующего: конфиг доезжает до конструктора,
  значит относится к структуре проекта, а структура при работе read-only.
- Запрет живёт **в ядре, а не в панели**: мутатор `project`, парный тому, которым правится свойство,
  отказывает при работающем пайплайне, а виджет только гасит поле. Иначе правило проверяемо лишь
  через Qt, то есть в `atp_ui_tests`, тогда как оно про структуру проекта и должно держаться и для
  MCP-клиента, который до панели не доходит.
- Введённый текст разбирается с показом ошибки; мусор в проект не пишется.

## Вне объёма

Сознательно не делается — перечислено, чтобы не всплыло как «забыли»:

- **Порты, зависящие от конфига.** Дверь открыта (значение уже в конструкторе), но C-путь остаётся
  статическим, и способ студии показывать порты до создания экземпляра не меняется.
- **Префиксы `file:` и `literal:`.** Грамматика их примет, реализация — отдельная задача: внешний
  файл тянет за собой циклы, отсутствующий файл, разрешение относительно каталога конфига и вопрос,
  что студия пишет при сохранении.
- **`"config"` у группы.** Разделяемость покрыта ссылкой; области видимости — отдельная затея.
- **Слияние ссылки с конфигом на месте.** Ссылка заменяет; смешивание изобрело бы семантику,
  которой никто не просил.
- **Порядок ключей, написанный в файле.** Чтобы он доезжал до модуля, документ пришлось бы читать как
  `nlohmann::ordered_json`, а это подписи `validate`, `decode`, `encode`, инструментов MCP и проекта
  сразу — правка, не имеющая к конфигу отношения. `config_value` упорядочен ради воспроизводимости
  обхода (раздел 1), и это всё, что он обещает.
